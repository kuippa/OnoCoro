# 模範プレイヤー プレイ想定モデル（Season 3 バランス調整用）

**作成日**: 2026-06-16
**目的**: 「模範的プレイヤー」の1プレイを定量モデル化し、移動時間・プレイ時間・必要コストを
見積もってバランス調整（初期予算・年の長さ・施策コスト）の根拠にする。
**対象マップ**: 三鷹井の頭５丁目

## 配置フローと所要時間の内訳

配置フェーズ（**タイマー停止＝untimed**）でプレイヤーが 1 施策を置くまで:

| 工程 | 所要 | 補足 |
|------|------|------|
| 1. 危険地点（ヒートマップのオレンジ建物）を確認 | 数秒 | 配置フェーズ開始時に表示 |
| 2. 設置候補地点まで移動 | **距離 D / 速度** | 走行なら D / 5.335 |
| 3. TAB でビルドメニューを開く → ビルド | 建設 2 秒 + UI 操作 ~2 秒 | ゲージ 2 秒 |
| 4. ストックから選択 → マーカークリックで配置 | ~2 秒 | |

**1 施策あたりの設置時間** ≈ `移動(D/速度)` + `約6秒（メニュー+建設+配置）`

---

## 計算式

```
1施策の設置時間 T_unit = D / V + T_op
   D    = 設置地点までの移動距離[m]
   V    = 移動速度（走行 5.335 / 歩行 2.0）[m/s]
   T_op = メニュー操作+建設+配置の固定オーバーヘッド ≈ 6 秒

年の配置時間 T_place(year) = Σ(各施策の T_unit)   ※施策間の移動も D に含める

1プレイの総時間（壁時計）
   = Σ_year [ T_place(year) + 年の実進行時間 ]
   年の実進行時間 = min(duration, 鎮火までの時間+4秒)

必要コスト = Σ_year (その年に置く施策のコスト合計)
```

## スキーム例: Year1 で「消火栓2 or 防火水槽1」

ユーザー提示のスキーム。仮に **移動距離 D=100m**（小マップ・スポーンから倒壊エリアまで・要実測）、
走行 V=5.335 m/s、T_op=6秒 とすると:

### 案A: 消火栓 ×2

| 項目 | 計算 | 値 |
|------|------|----|
| 1基の設置時間 | 100/5.335 + 6 ≈ 18.7 + 6 | 約 25 秒 |
| 2基の設置時間 | ×2（2基目の移動も D と仮定） | 約 50 秒 |
| Year1 コスト | 50×2 | 100 BIT |

### 案B: 防火水槽 ×1

| 項目 | 計算 | 値 |
|------|------|----|
| 1基の設置時間 | 100/5.335 + 6 | 約 25 秒 |
| Year1 コスト | 120×1 | 120 BIT |

→ **設置時間は案B（水槽1）が約半分**。コストはほぼ同等（100 vs 120）。
案A は「2 地点をカバー」、案B は「1 地点を広く」。教育的には「広域 vs 局所」の選択になる。

## 1プレイ全体の概算（3年・各年で同等の投資を継続と仮定）

- **年の実進行時間（timed）**: 60+90+90 = **240 秒（4分）**
  ※ただし鎮火が早ければ自動終了で短縮（実測では Year2/3 は施策成功時ほぼ即終了も）
- **配置フェーズ（untimed・壁時計）**: 1年あたり約 50 秒（案A）× 3年 ≈ **150 秒（2.5分）**
- **合計セッション時間**: 約 **6.5 分**（配置を含む。鎮火自動終了で短縮余地あり）

ワークショップでグループ討議を挟むと、討議時間が配置フェーズに上乗せされる。

## 要実測・要決定（次のアクション）

1. **平均移動距離 D の実測**: スポーン(37.4, 55, 37)から、各年の倒壊予定エリア（ヒートマップの
   オレンジ建物）までの距離。マップ上で代表値を測ると D が確定し、上記が実数になる。
2. **初期予算の決定**: 350 BIT に調整済み。ただし 350 でも全エリアをカバーできてしまう
   （＝施策が安い/効きすぎて scarcity が無い）ため、「どこに投資するか」の選択が成立していない。
   → 予算をさらに削るより、**施策コスト↑ or 効果半径↓ で「全カバーには予算が足りない」状態**を作るのが
   教育的トレードオフの本質。「限られた防災予算をどこに優先投資するか」を成立させる。

### PowerCube（Year2/3 で予算を稼ぐ案）について

- 効果: プレイ中に走って収集→ BIT 獲得。アクション性が増し「ゲームっぽく」なる。
- 懸念: 収入を増やす＝ scarcity を弱める方向なので、「全カバーできてしまう」問題には逆効果。
  また計画・投資中心（教育重視）からアクション・収集寄りに体験が変わる。
- 判断: 「全カバー問題」は scarcity 調整（コスト/半径/予算）で解くのが筋。PowerCube は
  「もっとゲーム性が欲しい」場合の任意フレーバー。導入するなら教育トーンとのバランスに注意。

### 倒壊建物のオレンジ表示の意味づけ（プレイヤーへの提示）

- 現状: ヒートマップのオレンジ＝地震で倒壊する建物（building_break 対象＝出火点）。
  一方、火災延焼で倒壊する建物はオレンジ無しで壊れるため、プレイヤーは
  「地震で必ず壊れる被害（避けられない）」と「火災で広がった被害（施策で防げた）」を区別できない。
- これは**教育の核そのもの**（地震倒壊 vs 火災延焼）なので、見える化する価値が高い。
  案: (a) 年開始時のテロップで説明（「オレンジ＝地震で倒壊・出火点。延焼を施策で防ごう」）、
  (b) 火災で倒壊した建物を別色（焦げ色/赤）にして地震オレンジと区別、(c) 両方。
3. **模範プレイの正解スキーム**: 各年に何を何個置けば被害を十分抑えられるか（DamageReportSystem の
   「抑えた延焼」がプラスになる最小構成）を実プレイで確定し、必要コストの下限を出す。
