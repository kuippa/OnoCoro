# Markdown Style Guide - OnoCoro ドキュメント表記規則

このドキュメントは、OnoCoro プロジェクトのすべての Markdown ファイルの表記方法を定義します。

**目的**: ドキュメント間の表記統一・可読性向上・エンコーディングエラー防止

---

## 1. 見出し階層

### ルール

- **H1 (#)**: ファイルタイトルのみ使用（ファイルごと1個）
- **H2 (##)**: メインセクション（ページの骨組み）
- **H3 (###)**: サブセクション（詳細説明）
- **H4 以下 (####+)**: 使用禁止（代わりに H3 + インデントで表現）

### 例

```markdown
# ファイルタイトル

説明文...

## セクション1

説明文...

### サブセクション1-1

説明文...

### サブセクション1-2

説明文...

## セクション2

説明文...
```

---

## 2. リスト形式

### ルール

**順序なしリスト**
- `-` を使用（`*` や `+` は使用しない）
- ネストは最大3階層まで

**順序付きリスト**
- `1.`, `2.`, `3.` を使用
- 階層ネストは避ける（必要な場合は説明文で補足）

### 例

```markdown
## 実装ステップ

- Step 1: ファイルを準備
  - サブステップ 1-1
  - サブステップ 1-2
- Step 2: コンパイル
- Step 3: テスト

## チェックリスト

1. 項目1の確認
2. 項目2の確認
3. 項目3の確認
```

---

## 3. テーブル

### ルール

- Markdown テーブル形式を使用
- セル内の改行は避ける（必要な場合は `<br>` でなく説明を別行に記載）
- 見出し行は必須
- セル幅は統一（視認性重視）

### 例

```markdown
| ファイル | 責務 | 対象者 |
|---------|------|--------|
| file1.md | 説明1 | Group A |
| file2.md | 説明2 | Group B |
```

## 4. コードブロック

### ルール

**インラインコード**
- `` `symbol` `` で囲む
- 関数名、クラス名、ファイル名に使用
- **日本語説明とセットで使用禁止** → 説明の後、別行で提示

**コードブロック**
- ` ``` ` で囲む
- 言語タグを指定（`csharp`, `powershell`, `markdown` など）
- 長いコード（10行以上）は コードブロックで提示

### 例

```markdown
関数 `GetComponent<T>()` を使用します。

```csharp
// C# の例
GameObject obj = GetComponent<GameObject>();
```

PowerShell での実行：

```powershell
Get-ChildItem -Path "Assets/Scripts"
```
```

## 5. 強調・リンク

### ルール

| 用途 | 記法 | 例 |
|------|------|------|
| **重要概念** | `**text**` | **Singleton Pattern** |
| **クラス名** | `` `ClassName` `` | `InitializationManager` |
| **メソッド名** | `` `MethodName()` `` | `ApplyStandardScalerSettings()` |
| **ファイルパス** | `` `path/file.md` `` | `docs/coding-rules/README.md` |
| _強調（副次的）_ | `_text_` | _推奨パターン_ |
| **リンク** | `[Text](path)` | [coding-rules](../coding-rules/) |

### ルール詳細

- **bold** は概念・重要用語に使用
- `code` は具体的な名前（クラス名、関数名、ファイル名）に使用
- 内部リンクは相対パスのみ使用
- 外部リンク（GitHub, 公式サイト）は必ず HTTPS

### 例

```markdown
クラス `GameManager` は **Singleton パターン** で実装されています。

メソッド `Initialize()` は [初期化フロー](../architecture/initialization-flow.md) を参照してください。

詳細は [GitHub](https://github.com/kuippa/OnoCoro) を確認してください。
```

## 6. タグ・マーク

### ルール

**禁止**: 絵文字（❌ ✅ 🚀 など）の使用

**代替**: 以下のテキストマークを使用

| マーク | 用途 | 例 |
|--------|------|------|
| `[OK]` | 実装済み・推奨 | `[OK] Canvas Scaler 設定完了` |
| `[NG]` | 非推奨・禁止 | `[NG] 公開フィールドの使用` |
| `[NOTE]` | 注釈・参考情報 | `[NOTE] 将来実装予定` |
| `[WARN]` | 警告・注意 | `[WARN] エンコーディング問題` |
| `[TODO]` | 実装予定 | `[TODO] UI システム統合` |

### 例

```markdown
## 実装チェック

- [OK] Canvas Scaler の設定
- [NG] public フィールドの直接使用
- [NOTE] フォント処理は将来実装予定
- [WARN] 大規模ファイルの Git 管理に注意
```

## 7. エンコーディング・絵文字

### ルール

**絵文字禁止の理由**
- Unicode 絵文字（U+1F*** など）がサーバー側でエンコーディングエラーを起こす
- ファイル更新時に 502 エラーが発生する可能性
- CI/CD パイプラインで検証エラー

**代替方法**
- テキストマーク（[OK], [NG], [NOTE] など）を使用
- 見出しの前に `##` を使用（区切り線は避ける）
- 箇条書きには `-` を使用

### 非推奨・推奨表記

```markdown
# 非推奨（絵文字使用）

✅ OK です
❌ NG です
🚀 実装開始
📋 チェックリスト

# 推奨（テキストマーク）

[OK] OK です
[NG] NG です
[TODO] 実装開始
チェックリスト（見出しで表現）
```

## 8. セクション区切り

### ルール

- 大きな区切りは `---` を使用
- 見出し前後の改行：見出しの前1行、後1行

### 例

```markdown
## セクション1

説明文...

---

## セクション2

説明文...
```

---

## 9. 参照・関連リンク

### ルール

**セクション末尾に配置**
- 関連ドキュメントへのリンク
- 相対パスのみ

### 例

```markdown
## まとめ

説明...

### 関連リンク

- [AGENTS.md](../../AGENTS.md) - AI Agent ルール
- [../architecture/](../architecture/) - システム設計
```

### 完全な Markdown テンプレート

```markdown

簡潔な説明（1-2行）

---

## セクション1

### サブセクション1-1

説明文...

### サブセクション1-2

説明文...

詳細説明：

- ポイント1
- ポイント2
  - サブポイント

---

## セクション2

| 項目 | 説明 |
|------|------|
| Item1 | Desc1 |
| Item2 | Desc2 |

コード例：

```csharp

{
    public void Method()
    {
        // 実装
    }

```

## チェックリスト

- [OK] 見出し階層が統一されているか
- [OK] 絵文字を使用していないか

- [OK] リンクが相対パスか

## 11. よくある間違い

### [NG] やってはいけないこと

```markdown
# [NG] 例1: 絵文字を使う
✅ 推奨パターン
❌ 非推奨パターン
🎯 目標

# [NG] 例2: リンクにコードを混ぜる
詳細は [../architecture/initialization-flow.md](../architecture/initialization-flow.md) を参照

# [NG] 例3: テーブルセルで改行
| ファイル | 説明 |
|---------|------|
| file1.md | 説明1<br>説明2 |

# [NG] 例4: H4 以上の深いネスト
#### H4 見出し（使用禁止）
##### H5 見出し（使用禁止）
```

### [OK] 推奨パターン

```markdown
# [OK] 例1: テキストマークを使う
[OK] 推奨パターン
[NG] 非推奨パターン
[TODO] 目標

# [OK] 例2: リンクをシンプルに
詳細は [initialization-flow.md](../architecture/initialization-flow.md) を参照

# [OK] 例3: テーブルセルは簡潔に
| ファイル | 説明 |
|---------|------|
| file1.md | 説明1と説明2 |

# [OK] 例4: H3 までで十分
## セクション
### サブセクション（H3 まで）
```

## 12. ロードマップ・マイルストーン の階層化

### ルール

**大規模ドキュメント（数百行以上）の場合は、以下のように分割する**：

- **上位層**: 全体ロードマップ（概要・進捗・マイルストーン）
- **下位層**: 各フェーズの詳細実装内容（詳細チェックリスト、工数見積もり）

### 背景

ロードマップは以下のライフサイクルを持つため、層分けが重要：

1. **活動中**: 頻繁に更新（進捗確認）
2. **フェーズ完了**: 詳細内容をアーカイブ
3. **参考資料化**: 過去の実装決定の記録として保持

**同じファイル内に両方あると**:
- アーカイブ時に不要な詳細内容が混在
- ファイルサイズが膨張して管理が煩雑
- 更新時に関連セクションの検索が困難

### 推奨ファイル構成

```
docs/_tasklist/
├── roadmap-phase-1-4-2-3.md          ← 上位層（概要・進捗）
│   └── マイルストーン、期間、成功指標のみ
│
└── detailed/                          ← 下位層（詳細）
    ├── phase-1-4-ui-improvement.md
    ├── phase-2-stage-gamebalance.md
    └── phase-3-qa-release.md
```

### ファイル分割の基準

**分割対象**:
- [ ] サブセクション（H3 以下）の内容が 200 行以上
- [ ] チェックリスト・テーブルが複数個
- [ ] 実装内容の詳細説明が 5 項目以上

**分割方法**:
1. 上位層ファイル: 見出し + 概要 + リンク（1-2段落程度）
2. 下位層ファイル: 詳細な実装内容

### 例

#### 上位層（roadmap-phase-1-4-2-3.md）

```markdown
# Roadmap: Phase 1.4～3

## Phase 1.4: UI 改善

**期間**: 2026-02-初旬～末  
**工数**: 10-14人日  
**進捗**: 25%

詳細は [phase-1-4-ui-improvement.md](./detailed/phase-1-4-ui-improvement.md) を参照してください。

| フェーズ | 進捗 | 期間 |
|--------|------|------|
| 1.4.1 | 0% | 2-3日 |
| 1.4.2 | 0% | 3-4日 |
```

#### 下位層（detailed/phase-1-4-ui-improvement.md）

```markdown
# Phase 1.4: UI 改善 - 詳細実装計画

## 1.4.1: Canvas Scaler 整頓

### 目標
...（詳細な実装内容）

### チェックリスト
...（30-50行の詳細チェック）
```

## 確認チェックリスト

新規ファイル作成時に以下を確認してください：

- [ ] **見出し**: H1 は1個、H2 からメインセクション開始
- [ ] **リスト**: `-` を使用、ネストは最大3階層
- [ ] **テーブル**: 見出し行あり、セル内改行なし
- [ ] **コード**: 言語タグ指定、インラインコードはシンボル用
- [ ] **強調**: **bold** は概念、`` `code` `` は名前
- [ ] **タグ**: [OK] [NG] [NOTE] [WARN] を使用、絵文字なし
- [ ] **エンコーディング**: 絵文字なし、UTF-8 で保存
- [ ] **リンク**: 相対パスのみ、外部リンクは HTTPS
- [ ] **セクション末尾**: 関連リンクを記載
- [ ] **ボリューム**: サブセクションが200行以上なら別ファイルに分割
