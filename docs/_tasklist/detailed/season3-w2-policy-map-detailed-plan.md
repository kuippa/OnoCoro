## 設計判断の記録（2026-06-12 ヒアリング結果）

| 論点 | 決定 | 理由 |
|------|------|------|
| 火災の視認性問題 | 小マップを新設（建物数の少ない PLATEAU シーン） | 体験設計の本命。「短時間で配置→消火を体験できる建物数が少ないマップ」（notes_season3.md 案 1） |
| 施策の効果モデル | 統計効果型（効果範囲内の被害率を下げる） | WaterTurret のリアルタイム撃退では延焼を止められない。「どこに投資したか」が結果を決める方が防災教育ツールとして筋が良く、W3 の ROI 計算と直結 |
| 床抜け（BUG-S3-002） | カメラシェイク化を W2 で実施 | DEM を動かさずカメラを揺らす方式へ変更し根本解消。オブジェクト・プレイヤーの奈落落下が無くなる |
| ヒートマップ | 簡易版（次年の倒壊予定/出火エリアの色付け） | 既存の doom マテリアル変更機構を流用して軽く実装。「どこが危ないか見てから投資する」体験を成立させる |

### Task 3: 統計効果型施策の実装（エージェント・2h）

施策 3 種を「効果範囲を持つ配置物」として実装する。

**データ定義**（YAML またはコード定数。W2 はコード定数で開始）:

| 施策 | コスト | 効果 | 範囲（目安） |
|------|--------|------|------|
| 消火栓 Hydrant | 50 | 範囲内の FireCube を周期的に鎮火（消火力 高） | 小 |
| 防火水槽 Cistern | 30 | 範囲内の延焼（FireCube 増殖）を抑制 | 中 |
| 避難広場 Plaza | 100 | 範囲内の人的被害補正（W3 の結果計算で使用。W2 では記録のみ） | 大 |

**実装内容**（2026-06-12 実装完了・検証待ち）:

- [x] `GameEnum.ModelsType` に Hydrant / Cistern / Plaza を追加

  毎秒の効果 tick で範囲内 FireCube のスケールを減衰させ、しきい値以下で鎮火（消滅）
  - [NOTE] 中央管理の InfrastructureSystem ではなく各ユニット自律駆動に変更（W2 規模では十分・実装が単純）

## タスク順序と分担

```
Task 1 カメラシェイク（エージェント）→ ユーザー検証
Task 2 小マップ（ユーザー Editor 作業と並行で エージェントが YAML 準備）
Task 3 施策実装（エージェント）→ Task 4 UI（エージェント）
Task 5 ヒートマップ（エージェント）
Task 6 検証（ユーザー目視 + エージェントログ解析）
```

Task 1 と Task 2 は独立しているため、ユーザーの Editor 作業時間が取れない週前半は
Task 1 → 3 → 4 を先行できる。

## リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| Cinemachine 構成でカメラ直接操作が効かない | Task 1 手戻り | 着手時にカメラ構成を調査してから方式決定（Impulse 候補） |
| 小マップの建物削除で PLATEAU 参照が壊れる | シーンエラー | 複製シーンで作業し原本は触らない。削除は建物 GameObject 単位に留める |
| 施策の TAB メニュー統合が既存フローに乗らない | Task 4 工数増 | 乗らない場合は YearPanel に専用ボタン 3 つ（W1 と同じ自己構築方式） |
| 統計効果のバランス（強すぎ/弱すぎ） | 体験の説得力低下 | W2 では効果を定数化して調整可能にしておき、バランス調整は W3 のデモ準備で実施 |
| 工数超過（合計 5h 超） | W3 圧迫 | 優先順位: Task 3 > 2 > 1 > 4 > 5。ヒートマップは最悪 W3 送り |
